## Evidence proves claims

A green command proves only what it exercised. Static, unit, schema, migration, integration, runtime, browser/device, visual/accessibility, security/privacy, financial/reconciliation and release evidence are distinct classes.

Bind material evidence to the exact candidate, relevant configuration/environment and claimed proof scope.

## Falsification

Before declaring an objective complete, try to disprove canonical ownership/readback, absence of stale writers/readers/config, authorization/negative cases, retry/replay/concurrency, timeout/unknown handling, compatibility/migration, required surface recovery, and external/financial reconciliation.

Documentation, a screenshot or green CI alone cannot substitute for materially required runtime/data/security/financial evidence.

## Interactive proof

Use the smallest tool capable of falsifying the claim. Browser automation proves material web interaction; device/mobile tooling proves mobile behavior; real devices are required when OS/background/permission/resource behavior is material; low-level diagnostics alone do not prove a user journey.

Trace material journeys through action → authorization → canonical effect → persistence/external effect → readback → final visible/system state, including failure/retry/recovery when relevant.

## Failure classification

Do not rerun until green without diagnosis. Classify implementation defect, environment/config mismatch, flaky/nondeterministic test, infrastructure/resource failure, external-provider failure, tool/dependency failure or unknown requiring diagnosis.

## Completion evidence

~~~text
AUTHORIZED OBJECTIVE = PROVEN
MATERIALLY AFFECTED CONE = ACCOUNTED
KNOWN MATERIAL OPEN OBLIGATIONS = 0
KNOWN LOSING/SHADOW AUTHORITIES IN CONE = 0
REQUIRED NEGATIVE / FAILURE / RECOVERY CASES = PROVEN
REQUIRED CANONICAL READBACK = PROVEN
BLOCKER = NONE
~~~

Do not expand into unrelated future Product breadth merely to satisfy a generic completion ritual.
